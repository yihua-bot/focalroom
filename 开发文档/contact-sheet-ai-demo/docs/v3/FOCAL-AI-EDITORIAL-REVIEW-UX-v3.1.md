# Focal AI｜Narrative Canvas 智能叙事草案交互规范

FocalRoom UX Specification v3.1 · 产品级设计 / 前端实现 / 后端协议 / Agent 行为 / 验收标准

## 一、核心设计：AI 不是替摄影师编辑作品，而是提出可以被审查和修改的创作方案

我建议把整个功能命名为：

AI Editorial Review — 智能编辑审稿

它不是普通的 AI 结果弹窗，而是嵌入 Narrative Canvas 的完整编辑审查模式。

用户可以让 Focal AI 基于现有画布生成多个叙事方案，看到每个具体改动的前后效果，自由选择采纳哪些改动，拒绝哪些改动，必要时回退已经应用的操作。

最终体验应该满足五个原则：

1. 先看再改：Agent 不得未经用户明确授权修改正式作品。
2. 所见即所得：用户预览的是采纳后实际会出现的画布，而不是仅看文本操作清单。
3. 局部可控：可以只采纳一张照片的位置调整、一个分组或一条编辑说明。
4. 随时反悔：每次采纳都形成独立的历史记录，支持撤销、重做和版本恢复。
5. 协作安全：原画布发生变化时，不能静默覆盖他人的修改。

### 与当前 GitHub 实现的差异

我核对了现有代码，发现你已经具备较好的基础，但这次需要做的是一次编辑审查机制升级。

| 交互能力        | 当前代码                   | 本次目标          |
| ----------- | ---------------------- | ------------- |
| AI 创建独立画布草案 | 已实现                    | 保留            |
| 草案与原版差异计算   | 已有 `canvas_comparison` | 升级为可交互的三方差异分析 |
| 新增、修改、移除统计  | 已实现                    | 可点击、筛选和定位     |
| 显示原版节点叠层    | 已实现                    | 分屏、叠层、按变更预览   |
| 采纳 AI 画布    | 已实现整板采纳                | 增加选择性采纳和合并    |
| 采纳后的撤销      | 尚不支持整板采纳撤销             | 增加事务级撤销和版本恢复  |
| 草案评论与审稿     | 有基础                    | 关联改动的评论、回复与决策 |
| 原画布版本冲突     | 已能检测                   | 三方合并、逐项解决冲突   |

这里有一个必须首先解决的产品缺陷：

当前 `NarrativeCanvas.tsx` 的“采纳画布”实际上是让草案 Board 变为正式 Board；界面明确写着“采纳操作无法撤销”。但用户通常希望的是：把 AI 草案中选中的修改应用回自己的原始画布，而不是得到另一张已经正式化的新画布。

这两种行为应当分开：

- 采纳到当前画布：将选定改动合并回源画布。默认行为。
- 保存为独立方案：保留一张新的作品画布，适用于 A/B 叙事探索。

这将是本次设计最重要的交互和数据语义调整。

## 二、完整 UI 架构

### 2.1 入口：从 Focal AI 对话自然进入审稿模式

不应要求用户先切换到“Agent 任务模式”。

例如用户在画布上对 Focal AI 说：

> “我觉得这组照片的中段不太连贯。你帮我重新组织一下，保留开头和结尾，给出两个不同的叙事方案。”

Agent 自动读取当前画布、所选节点、项目创作目标和已有审美反馈，在后台创建独立草案。

完成之后，直接在当前聊天中插入一张可操作的结果卡：

Focal AI · 叙事分析已完成

基于《日常》画布 v12 · 已检查 32 张照片

我发现中段连续出现了多张视角接近的远景照片，造成节奏重复。我准备了两种不同的编辑方向，原始画布保持不变。

方案 A · 节奏递进

移动 4 张 · 新增 2 条编辑说明

方案 B · 非线性呼应

调整 6 张 · 新建 2 个分组

目标 UI 示意。两个草案都有独立身份，可反复比较，不影响源画布。

选择方案后进入专门的 Review Workspace，而不是弹出只能滚动的确认对话框。

### 2.2 Review Workspace：建议使用三栏布局

桌面宽度 1440px 及以上时，建议采用：

- 左栏：240–280px，变更列表与筛选。
- 中间：弹性宽度，画布预览与比较。
- 右栏：320–380px，Agent 编辑理由、证据、批注和操作详情。
- 顶部：项目、草案、源版本、冲突状态及预览模式。
- 底部：采纳、另存与放弃操作。

### 2.3 三种预览模式

| 模式     | 交互                          | 目的          |
| ------ | --------------------------- | ----------- |
| 并排对比   | 原版在左、草案在右，同步缩放与平移           | 比较整体叙事结构    |
| 差异叠层   | 在原版上绘制 AI 建议的节点位置、位移轨迹、增删轮廓 | 精确判断局部修改    |
| 采纳结果预览 | 只模拟目前勾选的改动，未勾选的恢复原状         | 确认部分采纳后实际结果 |

第三种模式应作为默认模式，因为它回答用户最关心的问题：

“我如果只接受其中三条建议，最终画布究竟是什么样？”

并排模式、叠层模式、合并预览模式共享缩放、中心点和照片选择。切换模式不能导致视角突然跳回原点。

## 三、差异可视化：不仅要告诉用户改了多少，还要告诉他改了什么

现有 `canvas_comparison` 已经有 `add / change / remove`，但专业审稿需要更细的语义。

| 改动类型   | 视觉表达               | 右侧说明       |
| ------ | ------------------ | ---------- |
| 新增照片   | 新增节点轮廓 + 标记        | 为什么需要这张照片  |
| 移动位置   | 原位置虚框 → 新位置实框，显示轨迹 | 为什么要提前或延后  |
| 调整尺寸   | 变化前后边界             | 对视觉权重的影响   |
| 修改分组   | 分组区域变化，显示受影响节点     | 新的叙事主题与关系  |
| 修改连接线  | 旧线淡出，新线清晰展示        | 两张照片之间的呼应  |
| 删除节点   | 原节点半透明 + 删除标记      | 为什么建议移除    |
| 新增便签   | 直接展示文字内容           | 编辑逻辑及观察证据  |
| 切换调色版本 | 同一节点的两个实际渲染版本对比    | 色调与整组作品的关系 |

视觉设计上采用低饱和的中性色，加极少量状态强调色。但不能只靠颜色区分改动，必须搭配文字、轮廓样式和图标。

非常重要：所有比较叠层都不能改变照片像素本身的色彩解释。 原图、草案和合并预览应当使用同一套高保真图像渲染管线，界面标记在照片之外绘制，避免透明度叠加导致用户误判曝光或色调。

## 四、部分采纳：完整交互流程

这是整个功能的核心。

### 4.1 交互步骤

1. 选择改动

   每项改动左侧有勾选框，支持单项、全部、按类型选择和画布框选。点击改动正文仅负责定位和预览，不应直接改变采纳状态。
2. 自动处理依赖

   例如 AI 提议创建分组并把三张照片放入分组。只采纳分组而没有成员是不合法的。界面应自动提示所需的关联改动。
3. 即时模拟

   用户每次增减选择，系统都重新计算合并后的临时画布，不触碰正式作品。
4. 执行预检

   验证源画布版本、锁定节点、引用关系、权限、空间坐标和依赖操作。
5. 提交采纳

   服务器或本地领域层在一个事务内应用整组已批准的改动。成功后刷新正式画布。
6. 提供撤销入口

   显示“已应用 4 项变更 · 查看历史 · 撤销本次采纳”，同时持久记录合并事务。

### 4.2 一组改动可以拆到什么程度？

不要机械地以数据库写操作作为最小采纳单位。

建议定义 Editorial Change（编辑意图单元）。

一个编辑意图可以包含一个或多个底层操作。

例如：

编辑意图 #C-014：增强叙事中段的节奏变化

AI 建议把人物照片提前，并调整相关连接线。

将 IMG_017 移动到新的位置

重新连接 IMG_013 → IMG_017

默认作为一组采纳。如果用户只想移动照片，可以展开该意图，取消不必要的连接线操作，但必须重新验证引用关系。

原子性规则：

- 移动一个独立照片节点：可以单独采纳。
- 创建分组与加入成员：依据分组约束，通常组合采纳。
- 创建箭头：必须保证两个端点在最终画布中存在。
- 删除节点：必须处理连接线、节点锚定批注和相关引用。
- 修改调色版本：不能替换原始资产身份，只能改变所引用的 Rendition。
- 锁定节点：未经授权的 Agent 修改不能通过合并绕过锁定。

建议对每个改动记录 `requiredDependencies`、`optionalDependencies` 和 `conflictsWith`，由领域层计算合法的最终选择集合。UI 不应自己猜测依赖。

### 4.3 选择操作后的实时反馈

底部状态栏必须明确显示：

| 状态    | 文案                  |
| ----- | ------------------- |
| 没有选择  | 尚未选择改动              |
| 可采纳   | 已选择 4 项改动，可采纳       |
| 包含关联项 | 已自动包含 2 项必要的关联改动    |
| 含冲突   | 2 项改动存在冲突，请先解决      |
| 正在模拟  | 正在计算合并结果…           |
| 已完成模拟 | 预览已更新，正式画布尚未修改      |
| 提交中   | 正在应用改动，请勿重复操作       |
| 完成    | 已应用 4 项改动，可在历史记录中撤销 |

禁止仅靠“按钮由灰变亮”表达结果是否合法。

## 五、原始画布已修改：三方合并机制

这是多人创作不可省略的能力。

假设：

- AI 创建草案时，原画布是 `v12`。
- AI 修改草案，形成 `D5`。
- 摄影编辑在另一台电脑上，把正式画布改成了 `v14`。

此时用户点击“采纳”，绝不能直接拿 `D5` 覆盖 `v14`。

正确的数据模型是：

Base · B12

草案创建时冻结的源画布快照

Current · S14

当前正式画布，包含人工修改

Draft · D5

AI 建议的画布改动

Three-way Merge

对照 B12 → S14 和 B12 → D5，逐项判断改动是否冲突

### 冲突处理规则

| 情况                         | 系统行为        |
| -------------------------- | ----------- |
| AI 移动照片 A，摄影师修改照片 B        | 可以自动合并      |
| AI 移动照片 A，摄影师也移动 A         | 提示位置冲突      |
| AI 新增便签，摄影师没有修改相关区域        | 可以合并        |
| AI 移动已被摄影师删除的节点            | 禁止自动合并      |
| AI 修改照片尺寸，摄影师只修改了该照片的评论    | 通常可以合并      |
| AI 修改调色版本，摄影师同时修改同一节点的调色版本 | 需要人工选择      |
| 被改动的源节点已锁定                 | 阻止相应操作并说明原因 |

冲突界面提供三个动作：

保留当前修改 / 使用 AI 建议 / 手动调整

前两者用于解决单个可比较属性；第三个直接在合并预览中创建人工调整，重新生成预检结果。

用户不需要理解“乐观锁”“三方合并”等工程术语，只需要看到“第 17 张的位置已经被其他编辑修改”。

在没有完成三方合并实现前，最安全的过渡方案是：检测到源版本变化就阻止采纳，提供重新比较和重新生成草案。不能先允许覆盖，再打算补冲突处理。

## 六、撤销、重做和版本恢复

这里必须区分四种语义。

| 操作     | 含义              | 是否修改正式画布 |
| ------ | --------------- | -------- |
| 取消选择   | 不采纳某条 AI 建议     | 否        |
| 放弃草案   | 结束或归档未采纳的 AI 方案 | 否        |
| 撤销本次采纳 | 反向应用已经成功合并的修改   | 是        |
| 恢复历史版本 | 根据某个历史快照创建恢复操作  | 是        |

### 6.1 正常撤销

用户成功采纳 4 项建议后，系统将它们记录为一个逻辑命令组：

`AI Merge #M-204`

即使底层执行 9 次节点更新，在用户看来也应该是一次操作。

按 `⌘Z`：撤销整个命令组。

按 `⌘⇧Z`：在没有新分支修改阻断的前提下重做。

原有的 `canvas_op_log` 与 `command_group` 设计可以作为基础，但需要让 AI 合并事务明确接入历史栈。

### 6.2 撤销较早的一次采纳

假设用户采纳 AI 建议之后，又手工移动了其他照片。

之后他打开操作历史，选择“撤回三小时前的 AI 改动”。

这时候不能直接回滚整张画布，否则会抹除随后完成的人工编辑。

正确逻辑是：

1. 找出那次合并的实际操作集合及逆操作。
2. 检查后续操作是否依赖或覆盖了这些修改。
3. 无冲突时，生成一条新的“撤回”命令。
4. 有冲突时，先展示恢复预览，交由用户决定。
5. 保留原操作和撤回操作的历史记录。

这叫补偿式撤销，不同于直接恢复旧快照。

### 6.3 Undo History 的 UI

画布历史 ·《日常》

- v15 · 应用 Focal AI 方案 A

  移动 3 张、新增 1 条说明 · 用户批准

  查看差异 · 撤回此次修改
- v14 · 摄影师手动调整

  移动 IMG_021 · 解除节点锁定
- v13 · 摄影编辑调整叙事

  修改 2 张照片的位置关系
- v12 · AI 草案生成前

  原始创作版本，仍可查看及恢复

历史记录设计示意；撤回入口应根据权限和冲突状态决定是否可用。

验收原则：只要正式画布中发生了一次 AI 合并，就必须保留足以恢复、审计和解释该修改的数据。

## 七、批注与 AI 对话怎样结合？

我建议审稿界面支持两类评论，并保持明确区分。

作品评论：绑定正式画布节点、画布位置或出版页面，是长期创作记录。

草案审稿评论：绑定某条 AI 编辑建议或草案节点，是针对本次提案的讨论。

例如用户选择一条移动照片建议，并在右侧回复：

> “这张提前确实更连贯，但我不想失去原来第 15 张和第 16 张之间的停顿。”

Focal AI 应当理解这是针对当前草案局部结构的反馈，而不是重新解读整个项目。

然后显示：

“我保留第 15–16 张的位置，只调整第 17 张，并更新与之相关的叙事连接。是否在当前草案中生成修订版？”

确认后：

- 创建草案的新 Revision。
- 原草案版本仍可查看。
- 用户已明确采纳或拒绝的编辑意图保留其决策记录。
- 如果改动已实质改变，原有选择不能被静默沿用。
- 重新计算差异、依赖和冲突。
- 正式画布仍不变化。

这就把 Agent 变成可以持续沟通的摄影编辑，而不是一次性生成图片排列结果的机器人。

## 八、状态机与前后端工程契约

### 8.1 草案状态

| 状态                  | UI            | 允许动作        |
| ------------------- | ------------- | ----------- |
| `GENERATING`        | Agent 正在分析和编排 | 查看进度、取消     |
| `READY`             | 草案生成完毕        | 进入审稿        |
| `REVIEWING`         | 用户在选择和比较      | 切换预览、批注、选择  |
| `SIMULATING`        | 计算所选修改的结果     | 只读预览、等待     |
| `CONFLICTED`        | 源画布有冲突        | 解决冲突、重算     |
| `APPLYING`          | 正在提交合并        | 禁止重复提交      |
| `PARTIALLY_APPLIED` | 部分修改已采纳       | 查看剩余建议、结束审稿 |
| `FULLY_APPLIED`     | 全部修改已采纳       | 查看历史、退出     |
| `REJECTED`          | 用户拒绝方案        | 查看记录、重新生成   |
| `ARCHIVED`          | 已归档           | 只读查看、复制成新草案 |

这些是目标状态，不代表数据库现在已有相同枚举。

需要额外区分：草案的生命周期状态、单条变更的采纳状态、合并操作的提交状态。不能用一个 `state` 字段表达所有含义。

### 8.2 前端组件拆分

建议新增以下组件，而不是继续扩充目前超过 600 行的 `NarrativeCanvas.tsx`：

| 组件                         | 职责               |
| -------------------------- | ---------------- |
| `EditorialReviewWorkspace` | 整个审稿工作空间和布局      |
| `DraftSwitcher`            | 切换多个 AI 方案       |
| `ChangeListPanel`          | 改动树、筛选、勾选        |
| `CanvasComparisonViewport` | 并排比较、叠层和合并预览     |
| `ChangeInspector`          | 改动细节、证据、Agent 理由 |
| `ReviewCommentPanel`       | 草案评论和对话          |
| `MergePreviewController`   | 选择集合和模拟结果状态      |
| `ConflictResolutionPanel`  | 三方冲突解决           |
| `ApplyBar`                 | 底部主要动作与反馈        |
| `MergeHistoryPanel`        | 撤销、重做、历史恢复       |

画布渲染器本身应复用同一套节点和颜色管理能力，避免为“AI 审稿画布”另写一个简化的图片渲染器。

### 8.3 核心数据对象

建议在现有 `CanvasComparison` 的基础上新增下面的契约，字段仅展示关键部分。

```

type EditorialChange = {
  id: string;
  draftId: string;
  draftRevision: number;
  sourceNodeId?: string;
  draftNodeId?: string;

  kind:
    | "add" | "remove" | "move"
    | "resize" | "style" | "group"
    | "connector" | "rendition" | "annotation";

  title: string;
  rationale: string;
  before?: CanvasObjectSnapshot;
  after?: CanvasObjectSnapshot;

  requiredDependencies: string[];
  optionalDependencies: string[];
  conflictsWith: string[];

  evidenceRefs: string[];
  observedPhotoIds: string[];
};

type ReviewSelection = {
  draftId: string;
  draftRevision: number;
  targetBoardId: string;
  expectedTargetRevision: number;
  selectedChangeIds: string[];
};

type MergeSimulation = {
  simulationId: string;
  selectionHash: string;
  draftRevision: number;
  targetRevision: number;
  mergedSnapshotRef: string;
  effectiveChangeIds: string[];
  autoIncludedChangeIds: string[];
  conflicts: MergeConflict[];
  warnings: string[];
  canApply: boolean;
};

```

这里推荐保持 Change 的身份稳定，但每次审稿请求必须带上草案版本和目标画布版本。若草案内容变更，不允许以旧差异 ID 偷换新内容。

另外，`rationale` 不应冒充“已经观察过图片”的证据。视觉判断必须能关联实际观察记录、照片版本和模型执行来源。

### 8.4 核心接口

桌面端 IPC 与云端 HTTP 可以采用不同传输，但领域行为应当保持一致。

| 接口                    | 输入                   | 输出                     |
| --------------------- | -------------------- | ---------------------- |
| `GET draftComparison` | draftId、源画布与草案版本     | 变更清单、原始快照、冲突信息         |
| `POST simulateMerge`  | 选择的 changeIds、目标版本   | 合并预览、依赖、冲突             |
| `POST applyMerge`     | simulationId、版本、幂等键  | mergeId、正式画布新 revision |
| `POST rejectChanges`  | changeIds、理由         | 变更决策记录                 |
| `POST revertMerge`    | mergeId、目标版本、幂等键     | 撤回结果或冲突列表              |
| `GET mergeHistory`    | boardId              | 审批、采纳、撤销的历史事件          |
| `POST reviewComment`  | changeId 或 anchor、正文 | 可追踪的评论线程               |

尤其是 `applyMerge`，必须在数据库事务中完成：

- 重新验证草案及目标画布版本。
- 校验批准人的权限、节点锁及引用关系。
- 重新验证 simulation 与所批准改动一致。
- 生成必要的新节点 ID 及源/草案 ID 映射。
- 应用全部批准操作。
- 写入变更历史、逆操作、审批者和来源。
- 一次性推进正式画布 Revision。
- 返回持久化的幂等回执。

不能出现节点已经移动，但历史记录没有保存的中间状态。

已有 `canvas_execute` 的事务化命令与幂等回执机制可以复用，但需要新增专门的 ApplyEditorialChanges 领域命令，而不是把现有 `AdoptBoard` 当作部分采纳接口。

## 九、权限、异常和可访问性

### 权限矩阵

| 角色       | 查看草案    | 评论   | 建议采纳 | 实际合并            | 撤销正式合并 |
| -------- | ------- | ---- | ---- | --------------- | ------ |
| Owner    | 是       | 是    | 是    | 是               | 是      |
| Editor   | 是       | 是    | 是    | 根据项目权限          | 根据权限   |
| Reviewer | 是       | 是    | 是    | 否               | 否      |
| Viewer   | 是       | 否    | 否    | 否               | 否      |
| Focal AI | 任务授权范围内 | 提供建议 | 创建草案 | 否，除非明确授予特定自动化权限 | 否      |

云端必须由服务端校验权限。按钮隐藏不等于权限保护。

### 异常处理

| 场景         | 用户体验                        |
| ---------- | --------------------------- |
| AI 生成中断    | 保留已完成的可验证草案内容，允许恢复或重新生成     |
| 源文件失联      | 显示缺失资产，禁止冒用其他照片替代           |
| 原画布已更新     | 提示版本变化，重新计算三方合并             |
| 网络中断       | 本地审稿选择可保留；共享项目禁止未经确认的正式写入   |
| 提交后网络断开    | 使用同一幂等键查询回执，禁止自动重复创建合并      |
| 修改了锁定节点    | 指出具体节点，允许排除该改动              |
| 草案使用了新调色版本 | 明确呈现原版与新渲染版的差异              |
| 1000+ 节点画布 | 按视口加载和虚拟化列表，不能一次性渲染全部高分辨率图像 |
| Agent 生成失败 | 显示可重试原因，不把未完成草案标记为可采纳       |

### 快捷键和可访问性

| 操作          | 快捷键建议             |
| ----------- | ----------------- |
| 选中当前改动      | `Space`           |
| 上一项 / 下一项改动 | `↑ / ↓`（焦点在改动列表时） |
| 切换原版 / 草案比较 | `⌘1 / ⌘2`         |
| 切换合并预览      | `⌘3`              |
| 适合画布        | `Shift + 1`       |
| 撤销正式修改      | `⌘Z`              |
| 重做          | `⌘⇧Z`             |
| 退出审稿模式      | `Esc`（无未完成编辑或操作时） |

评论输入和文本编辑拥有焦点时，不允许全局快捷键误触发画布操作。

必须有完整键盘导航、焦点恢复、VoiceOver 语义、触屏与触控板适配，并支持减少动画。需要解决颜色不可见用户如何区分“新增、移动、删除”等视觉差异。

## 十、研发实施拆分与验收标准

我建议分成六组依赖任务，不按单纯 UI 页面拆。

| 任务组          | 主要交付                | 核心验收                     |
| ------------ | ------------------- | ------------------------ |
| R1：差异契约      | 属性级变更、稳定身份、依赖关系与源版本 | 同一草案重新读取得到一致 diff        |
| R2：视觉比较      | 三种预览模式、高保真渲染、定位     | 缩放和平移切换不跳变；颜色一致          |
| R3：选择性模拟     | 勾选、依赖闭包、合并预览、预检     | 所见预览与正式应用后的结果一致          |
| R4：安全合并      | 事务提交、幂等、权限、三方合并     | 不丢人工修改；失败不部分写入           |
| R5：撤销历史      | 合并命令组、逆操作、版本恢复      | 撤销只影响对应操作，不误伤之后的编辑       |
| R6：Agent 与协作 | 对话关联、审稿评论、权限、实时状态   | AI 可以多轮修改草案，审批人始终掌握最终写入权 |

### 必须通过的 12 个端到端场景

| #  | 测试场景                    | 通过条件                |
| -- | ----------------------- | ------------------- |
| 01 | AI 修改 20 个节点，仅勾选 3 个    | 只有所选及必需依赖改动被应用      |
| 02 | 新增分组但未选择必要成员            | 自动提示依赖或阻止不合法操作      |
| 03 | 只移动一张照片                 | 其他节点坐标、样式、版本不变化     |
| 04 | 源画布在审稿过程中变化             | 正确识别冲突，不覆盖人工修改      |
| 05 | 两个用户同时采纳草案              | 只有合法版本写入；另一个收到明确冲突  |
| 06 | 提交后网络断开并重试              | 不产生重复节点或双重历史        |
| 07 | 采纳包含多项修改后按撤销            | 一次撤销完整命令组           |
| 08 | 已采纳后又发生人工修改，再撤回 AI 改动   | 保留不相关的人工修改          |
| 09 | 草案中的照片被锁定或删除            | 不能绕过约束，显示具体原因       |
| 10 | Agent 修订已进入审稿的方案        | 失效选择重新确认，不静默套用      |
| 11 | 使用 16-bit TIFF 与广色域图像对比 | 专业色彩渲染与真实版本一致       |
| 12 | 应用后关闭应用并重新打开            | 草案、审批、变更历史和回退关系完整保留 |

特别要增加基于属性和随机操作序列的测试：连续移动、分组、删除、撤销、重做、冲突解决后，数据库与渲染快照的节点关系必须保持一致。

## 十一、最终用户体验示例

摄影师打开《日常》项目，当前 32 张照片已经编排成一条初步序列。

他对 Focal AI 说：

> “请保留开头的城市远景和结尾的人物肖像，重新编排中间部分。我想要一种逐渐从疏离转向亲密的感觉，但不要做得太直白。”

Agent 完成观察后，创建方案 A 和方案 B。

摄影师打开方案 A，在叠层视图中看到 4 张照片被移动、2 张被并置，另有一条编辑说明建议减少中段的重复感。

他只喜欢其中 3 个改动。

他勾选这 3 项，系统自动计算合并预览。确认满意后，点击“采纳选中改动”。

正式画布生成 `v13`。用户随后觉得某个位置仍不合适，按 `⌘Z`，撤销整次采纳，再通过聊天要求 Agent 重新考虑第 14–18 张。

Agent 在原草案基础上创建修订版本，不需要重新从 32 张照片开始分析。

整个过程没有丢掉原始画布、人工批注、照片身份、调色版本和之前的叙事判断。

这才是我们希望实现的持续创作关系。

### 最终产品决策

我建议将 AI Editorial Review 作为 FocalRoom 核心创作体验的一部分，而不是新增一个独立的小工具。

最终用户感知到的应该是：

Focal AI 会提出想法，摄影师可以直观理解它、选择它、修改它、反驳它，甚至在采纳之后反悔。

对于 FocalRoom 的专业定位，这比“AI 自动整理画布”更有价值。AI 不应取代摄影师的审美决定，而应通过高质量提案和精准、可逆的交互，提高摄影师探索不同作品可能性的能力。

本规范可以作为新一轮研发的 UI/UX 与领域交互基线。需要明确的是：部分采纳、三方合并与可撤销采纳属于新增目标能力；当前仓库还没有完整实现，不能直接用现有的“整板采纳”操作替代。
