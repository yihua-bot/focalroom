# v2.0 M0 数据兼容与迁移评审方案

日期：2026-10-15。当前 schema 版本：10。本轮不增加或执行生产结构变更。

## 当前阶段采用的兼容策略

现有 projects/photos/sequence_items/versions 与 command_events、Agent、记忆表继续为唯一持久化来源。v2 M0 只引入类型、Schema、纯权限测试和独立工程入口。不要执行新包 `db/local/0001_local.sql`，不要复制历史数据到第二套 local_* 表。

所有现有项目仍是本地项目；代码未暴露共享按钮，也未从内存类型推断旧项目已经迁移。旧 v1 回执、ID、revision、人工撤销栈与任务恢复协议均保持原样。

## 下一次数据库变更的候选范围（尚未实施）

新增迁移须在 Creator/Workspace 身份设计确定后编写，预期只做加法：

1. 建立本地 creator 与个人 workspace 的稳定 ID，明确首次初始化与恢复时如何复用；不能拿用户名、设备路径或文件名充当身份。
2. 在既有项目上建立归属与模式元数据，全部旧项目回填 LOCAL；mode 与本地副本状态分开，受约束的组合明确列出。
3. 原照片、版本、证据等保留 ID。证据/假设归属 creator，项目协作成员不自动获得私人记忆。
4. 在正式命令的可信入口增加单权威检查。PROMOTING/SHARED_CACHE 状态不能由旧 IPC 旁路继续写入；只新增列而不保护旧入口不能通过验收。
5. 同一数据库事务内完成模式状态、迁移清单与相关回执；真实云 Promotion 分阶段协议留 M4。
6. 旧任务、回执快照是否需要补默认字段必须逐项定义；不要重新序列化历史 fingerprint，不能重放出重复草案或人工记录。

## 验收与回滚

先使用临时数据库与独立评审 identifier：

- 含 WAL 的旧库备份必须包含已提交内容；升级失败时原数据可由备份恢复。
- v1 命令回执重放、Undo/Redo、版本恢复、旧任务中断恢复继续正确。
- 项目、照片、序列、版本、证据、假设、事件逐项核对；源文件 hash 不变。
- 受保护的跨项目/工作区引用被拒绝；模式切换中重入、失败、重启均不产生双主。
- 本地与云端没有双向可写镜像。云创建成功但本地确认失败时，必须可查询 operation ID 恢复，不能静默回退本地继续提交。

数据库结构变更属于本会话 AGENTS.md 要求明确确认的操作。在评审具体迁移、影响和备份恢复证据后，再请求确认实施；本轮继续完成其他不依赖该变更的 M0 工作。

M0 的兼容测试通过既有迁移建立临时库、验证外键和事务回滚，再重开逐项比对项目；完整旧版本升级与版本/历史旅程由既有回归覆盖。这些证据不等于以上候选迁移已实施。
