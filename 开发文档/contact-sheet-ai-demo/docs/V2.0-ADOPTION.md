## 产品方向变化

核心目标是摄影创作与协作工作空间：专业摄影 Agent、独立可用的 GUI、多人审稿和提案审批，随后验证私密专业服务。

1. Agent 质量成为先行验收门槛：至少 30 个合法授权任务，按摄影意图、事实、序列节奏和审稿价值进行专家评价；不能用 Mock 轨迹或模型自评代替真实质量。
2. 项目引入两种权威模式：LOCAL 由本地 Rust/SQLite 管理；SHARED 由云服务/Postgres 管理。共享迁移必须显式，失败可恢复，不产生双主。
3. Web 从示例预览扩展为真正的受邀审稿端；桌面保留本地原图、离线编辑和媒体处理。
4. 作者私人记忆与项目协作知识分开授权。加入工作区、共享项目或服务订单，不自动共享个人偏好。
5. 正式序列、审批和版本继续使用可信命令、事务与 revision；Presence 等暂态信息才采用限定范围的 CRDT。
6. 团队、教育、订阅与服务订单分阶段推进。专业服务先验证邀请式成交与交付，再考虑公开目录。

## 新旧契约的实施前决策

需在 v2.0 M0 形成架构 ADR，明确以下映射后再改代码：

- **工程组织**：逐步将现有桌面入口接入 `apps/desktop`，共享 UI/契约进入 packages；Web 独立构建。云 API 与 worker 初期仅为清楚标识的 skeleton，不宣称具备协作能力。
- **可信身份**：现有 CommandContext 是单机人类/只读边界，不等同于多人 ACL。新建 Creator/Workspace/Project/Task principal 契约，身份来自可信入口，客户端和模型不能自报审批权限。
- **协议版本**：现有 camelCase GUI 命令与新 snake_case envelope 使用显式版本和适配层；保留旧命令回执、幂等指纹、历史与任务检查点的兼容性。
- **审批语义**：统一 Proposal 操作 ID、base revision、审批范围及 nonce；新包 `accepted_operations` 与 `accepted_operation_ids` 命名需统一或明确映射。正式审批仍不成为 Agent 工具。
- **项目权威**：区分业务模式 LOCAL/SHARED 与客户端的 PROMOTING/SHARED_CACHE 状态；M0 先定义和测试边界，真实 Promotion 在 M4 实施。
- **旧库升级**：现有迁移为 0001–0010，新包 local SQL 不能覆盖它们，也不能直接新建一套与旧业务并行的权威表。需制定默认 LOCAL、旧照片/版本/证据归属、备份及回滚方案，再以新增迁移实施。
- **资源与记忆**：保留现有 photo ID 与 hash；共享 Asset 引用、作者私有记忆和项目评论分别定义归属。不得因同图 hash 命中而跨越授权域。
- **媒体与费用**：当前 1400px 视觉预览与新共享预览默认 2048px 属不同用途；原图检视也需单独设计。旧费用单位与新 microusd 必须显式换算，不能直接扩大预算常量。
- **依赖**：保护现有 lockfile；实施时核对并记录可构建版本。仅为未来模块不引入整套运行服务，不在本轮升级核心依赖。

## 需求包静态检查与设计缺口

本轮运行 `python3 tests/verify_contracts.py`：通过。检查覆盖 JSON 解析、Schema 元结构、工具名称、验收索引、本地内存 SQLite 建表和基本外键；不证明应用实现或 PostgreSQL 可部署。

新包包含 14 个工具描述与 24 条验收索引，均为待落地的目标。额外使用本地 JSON Schema 与内存 SQLite 复查得到：

1. `photo.set_selection`、`proposal.create`、`comment.add` 的空 payload 被接受；除少数命令外仍须补 discriminator 分支、字段约束、错误及结果契约。
2. `local_sequence_items` 可以将项目 B 的照片放入项目 A 的序列。生产契约需由可信领域层拒绝，并考虑组合外键/触发器形成第二防线。
3. 原型任务与提案状态枚举需和运行时 planning、interrupted、needs_input、changes_requested 等语义进行版本映射，不能直接替换并破坏恢复。
4. 生产级共享鉴权、邀请、审批记录、审计、序列等设计不能仅依赖当前 SQL 样例；RLS 注释不等于已经建立租户隔离。
