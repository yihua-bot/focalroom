# ADR 0002：接入 v1.0 最终 Agent 实施基线

日期：2026-10-13。状态：需求已接入；运行时实现待分阶段执行。取代 ADR 0001 的后续需求优先级，保留其中与 v1.0 一致的原图只读、统一状态和兼容迁移原则。

用户提供 v1.0 需求包。以主 Markdown 规格作为后续基线，将 13 个原始文件带 SHA256 归档至 planning-v1.0；v0.2 作为历史参考。复用当前单 package Tauri/React/Rust/sqlx/image 工程及锁文件，不因参考 monorepo 目录重建应用。这是对已有工程的实施取舍，符合 KISS/YAGNI。

先按 v1.0 M0 复核/补齐 GUI、200 张测试图→25 张序列的离线重启门禁；真实摄影师图库不作为这一 M0 基础实现的前置条件。M1 实现统一 CommandHandler、持久化幂等、事件、版本与撤销。M2 提供接受 ModelOutcome 的动态 Runtime、受控工具、草案、预算和恢复；不同观察必须改变后续轨迹，不能用固定 pipeline 代替。

可信身份由 GUI/审批/工具执行通道派生，Agent 只能写草案，正式批准仍需用户显式动作；预算与 consent 在后端确定性检查。IPC、Provider、PolicyGate、事务领域服务保持职责分离（SRP/DIP），正式状态和幂等写入共享事务边界（DRY）。

原始草案工具 schema 与 §6.1 items 示例有冲突，后续以主规格修订工程契约并同步 DTO/测试，原始包不改。现有旧库和已经应用 v0.2 的库需分别做兼容升级，保留旧 migration checksum；单独追加 0002 不会修复旧 agent_tasks 的 paused CHECK。未经升级验证不对实际库应用新包初始 SQL。

M2 可以使用明确标注的模拟反馈验证 Runtime 自主分支，不能据此宣传真实视觉或真实记忆已完成；视觉在 M3，记忆在 M4。评分、预算 token/input 配额、receipt 与审计表关系等剩余契约差异见 [V1.0-ADOPTION.md](../V1.0-ADOPTION.md)。
