# 验证码修复的生产部署方案

日期：2026-10-18。目标仅为 `root@1.13.251.21:/opt/focalroom` 中的 FocalRoom API/Web 及其独立数据库。保留现有官网、Cloudflare Tunnel、数据库和预览卷，不操作 openyc。**当前未执行部署；SSH 认证被拒绝。以下是分阶段方案，不是可盲目执行的一键脚本。**

## 1. 先取得只读核对结果

管理员在本机 SSH 配置中提供可用主机别名或 IdentityFile；不要在聊天中粘贴密码、私钥、Resend key 或 .env 内容。

只读确认：主机架构、`/opt/focalroom` 路径、Compose project 标签、API/Web/Worker/PG 的实际镜像 ID、容器退出状态、挂载和反向代理路径；读取必要且脱敏的 API 错误，不转储环境变量。比较待部署文件 SHA256，辨别是旧源码、错误构建上下文、权限、数据库版本，还是其他原因。

数据库只读核对已登记迁移的 version/sha256、表结构、所有者和应用/迁移角色；与 `apps/api/src/database.ts` 的清单比较。预期登记顺序为 0001、0002、0006、0008、0010、0011、0009（min_privilege_grants）、0012。目录中 0003–0005、0007 和旧 0009_magic_login 草案不能按文件名全部执行。未知迁移或校验和不符时停止，不改历史记录强行通过。

已有 PG 卷不会重新执行 postgres-init；若线上还没有最小权限角色，须单独制定并批准角色/所有权转换，不能认为重建容器会自动补齐。当前本地通过不证明生产拓扑与此一致。

## 2. 冻结待部署源码并构建，暂不替换服务

以本轮报告和 `source-sha256.json` 为核对入口；上线前重新冻结完整部署快照并复跑检查，避免把其他进程未验收修改一起带入。传输上下文排除 .env、私钥、用户照片、数据库和 node_modules，不覆盖服务器配置。提交/推送须另有明确授权。

在目标架构构建 API/Web 独立新 tag，记录镜像 ID/digest。不要直接部署本机 aarch64 镜像，也不要通过删除所有镜像、builder prune、compose down 排查缓存。Docker 的 COPY 缓存会考虑文件内容；先比较源文件与镜像内摘要，再决定是否有必要 --no-cache。

使用 `USER node` 实际导入 server.ts，并检查 rate-limit.ts、magic-login.ts、0012 SQL 可读；用独立测试库和 Nginx 验证正常镜像 CMD。构建与验证不需要停止生产数据库。

## 3. 配置、备份与迁移前的批准点

- `FOCALROOM_WEB_ORIGIN=https://team.focroom.cc`，须是精确 Origin；Nginx 同源代理保留 Origin/Upgrade。
- 在服务器受控配置中提供已验证发送域的 `FOCALROOM_EMAIL_FROM` 和 Resend key；不打印或提交这些值。未配置时服务会明确返回 503。
- 保留现有 Tunnel 和 TLS 配置。Tunnel 到本机 HTTP 源站不构成切换 Cloudflare SSL 到 Flexible 的必要理由，不能用降低 TLS 校验解决本地 API 崩溃。
- 保持 PG 和 API 非公网暴露；核对现有回环绑定是否适配 Tunnel 运行方式，不直接套用本地 Compose 覆盖线上配置。
- 核实所有写入者，包括 API 副本和 Agent Worker；维护窗口内统一停写。现有备份工具只自动暂停 API，若 Worker 正在运行，管理员须一并协调，不能把不一致快照当成备份完成。
- 完成独立数据库 custom dump 和磁盘预览对象的一致性备份、校验、记录旧镜像与配置；备份工具边界见 `ops/shared/README.md`。R2 场景需要另行对象备份方案。

以上目标、远端差异及停写/角色方案明确后，再请用户一次性确认该生产更新：涉及短暂停写、新增验证码表/失败计数和授权的 0012 迁移，以及 API/Web 重建；不涉及删除数据库/卷或其他项目。

## 4. 批准后的执行顺序

1. 按已核对拓扑停写并验证备份可读，记录旧容器/镜像及状态。
2. 用独立迁移角色运行**新镜像**的 `node apps/api/src/server.ts --migrate`，明确连接 FocalRoom 独立库；普通启动不会自动执行 DDL。
3. 只替换批准范围的 API/Web。Worker 是否同步替换取决于源码差异和已批准清单，不顺手开启模型或新服务。保留 PG 容器/卷和现有 Tunnel。
4. 先从服务器回环确认 HTML/静态资源 200、代理 `/api/v2/auth/me` 401、容器无启动错误；再检查公网 HTTPS 页面和新标题，必要时调查浏览器/CDN 缓存，不全局清缓存。
5. 经用户明确指定接收邮箱，实际发送验证码；确认邮件可达、登录 Cookie 为 HttpOnly/Secure、刷新保持会话、项目与批注正常、退出后鉴权失效。不向随意编造的真实邮箱发测试邮件，不对真实作品发布测试批注。
6. 恢复批准的写入者，核对请求错误率和任务队列，记录最终源码/镜像/迁移摘要及实测结果。只有此时才能宣布线上恢复。

## 5. 回退边界

`assertSchema` 严格校验迁移数量和 SHA256；0012 应用后，旧镜像可能因未知 schema 拒绝启动。因此“直接切回旧镜像”不是完整回退方案。上线前准备兼容新增 schema 的备用镜像，或在停写状态把备份恢复到独立目标并验证后，经批准切换；不删除迁移记录、不逆改历史 SQL、不清空原库。

本轮已完成本地工程验证，尚未确认生产邮件、远端权限、已登记 schema 或生产恢复能力。SSH 可用后先完成第 1 阶段，不能跳过核对直接实施以上命令。
